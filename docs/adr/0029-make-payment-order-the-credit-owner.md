# Payment Order 拥有支付事实及完整充值事务

本次在线充值由一张 Order 拥有。Order 在生成可付款表单或调用远端预下单之前持久化，冻结用户、网关身份、产品、订单应付总额、币种、额度、地址及本地展示截止。`(user_id, request_key)` 保证同一次操作重试仍使用原订单和原报价；SQL `new → claimed` 声明确认后才执行首次准备。

本地签名交付与远端创建是不同产品能力。远端创建结果不明时保留 `unknown`，只认证查单、等待通知或人工核查，不重放创建。超过准备 deadline 不授予第二次远端创建权；纯本地表单可以恢复同一冻结动作。

回调和认证查询均形成 `PaymentObservation`，再进入唯一的 `CompleteOrderPayment`。成功证据必须完整匹配原订单、网关、商户、环境、供应商交易命名空间、稳定交易引用和订单应付总额。`users.quota`、晋级组及 Order.paid 在同一 SQL 事务中提交。ACK 由适配器在事务结束后生成；观察过程不写 HTTP 或 SQL。

交易唯一性使用 `(transaction_namespace, provider_transaction_id)`，不按本地 GatewayID 拆分供应商真实交易空间。尚未取得交易引用时保存 NULL，已有真实非空引用不因未付款或未确认而清除。订单应付总额使用最小货币单位，报价只在最终落单时 HALF_UP；优惠后用户实付与商户净结算额不代替应付总额。

身份与凭证分别管理。商户、应用、环境、端点作用域和协议 profile 不通过普通编辑改变；同主体凭证通过 revision + SQL CAS 轮换。停用与软删除阻止新单，历史通知、查单与凭证维护仍使用原身份。资源组按网关与 revision 隔离，退役等待在途句柄和后台任务退出。微信使用官方 SDK 的独立证书下载器，适配器拥有串行刷新、取消和退出等待；不使用在持锁期间等待后台任务的 SDK manager。APIv3 密钥轮换需协调商户侧服务，不承诺旧通知密文始终能被新密钥解密；无法验证的通知不入账，通过认证查单恢复原单事实。

## 影响

- `preparation_state`、`payment_state` 与 `window_state` 分别表示动作准备、资金事实和动作交付资格。本地到期不拒绝合法迟到付款。
- 前端确认冻结金额后复读原单，使用服务端时间和当前截止交付动作。该检查不承诺浏览器与供应商付款原子提交。
- Payment Order 与消费 Billing Attempt 是不同 owner，不推导消费侧具有持久去重保证。
- 晋级沿用余额加已消费额度的口径，不另存充值累计或区分入账来源。充值、兑换、奖励及管理员增减共用事务内余额与晋级逻辑；本次增减只计一次。兑换保留独立 owner。
- 不增加通用账本、创建重试、双写或迁移态。上线前必须完成 [U1 停机升级签收](../deployment/payment-v2-upgrade.md)，历史记录不得再次增加现有余额。
