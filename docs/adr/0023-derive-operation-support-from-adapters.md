# Derive operation support from adapters

Public operation support is a model-independent fact of the proxy adapter, not an administrator claim about an upstream product. The proxy therefore derives support from its installed adapters and removes `other.capabilities.operations`; when an adapter can faithfully relay an operation, the request is sent and the real upstream decides whether its endpoint or account accepts it. Local fail-closed errors are reserved for operations the proxy cannot represent, while Stored Response ownership and exact-channel routing remain proxy responsibilities.

Candidate-level representability rejection is a selector filter, not a blanket replacement for every later selection error. After selection fails, the routing snapshot is classified with the same request-static filters while deliberately ignoring runtime cooldown/disable state: `unsupported_capability` is returned only when every configured candidate is unrepresentable. If any compatible candidate exists but is unavailable, the availability error remains authoritative; request cancellation and deadline always take precedence.

Two explicit choices remain because they describe proxy behavior rather than upstream capability: `compatible_response` opts into Responses-to-Chat cross-protocol conversion, and an unknown compatible endpoint requires an opt-in before the proxy attempts native Responses WebSocket transport. The existing `channel.Other` JSON is the sole configuration owner for `responses_ws_native` and `responses_ws_self_hosted`; the Web UI exposes Other(JSON), validates the value, and shows the self-hosted warning without maintaining mirror switches. No channel columns are added. Model availability and aliases remain exclusively in channel model configuration and model mapping. Adapter operation support and pricing are not inferred from model names. A documented Responses-only model is the narrow exception for the public Chat compatibility endpoint: it requires a Responses-capable candidate and uses the existing explicit Chat-to-Responses adapter instead of sending an invalid Chat Completions request upstream.
