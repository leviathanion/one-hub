# Fail closed on ambiguous WebSocket lifecycle events

> ADR-0030 保留本文的 fail-closed 与 no-replay 边界，但取代“保留或收取 quota floor”的计费决定；ADR-0033进一步规定按原子Price Component判断哪些provider evidence可收费。

A `response.create` turn becomes visible to the receive path before its upstream write begins. Once `WriteMessage` is entered, an error cannot prove whether the provider received the request, so the proxy does not replay the same side-effecting create and fails the connection closed. Closure always uses ADR-0030：有 provider usage 才收费，否则释放 reservation。

A Realtime top-level `error` without usable event or response correlation remains ambiguous and fails the connection closed. Native Responses WebSocket has a different contract: the protocol permits only one in-flight response, so an ordinary request-level `error` belongs to that active attempt; the actor delivers it unchanged, settles and releases that turn, then advances the bounded FIFO without replay. Only an explicitly classified connection-level error closes the Responses WebSocket. Codex attachment takeover transfers already accepted outbound events to the replacement mailbox, while reader-generation teardown discards only stale transport events and releases their shared byte credits. Provider terminal/error admission and attachment handoff are serialized by the execution-session lock, so an old WS reader cannot strand a permanent `Inflight` turn during takeover.

OpenAI Realtime `response.created` may originate at the provider through VAD or idle-timeout policy without a client `response.create`. one-hub cannot observe a per-turn Work Action before that provider work starts, so this path is the sole post-work observation settlement exception to the ordinary TCC boundary. The first correlated `response.created` establishes a separately observable turn keyed by the provider response ID, fixes the connection's principal and execution attribution, and creates a zero-reservation observation owner without a Submission Claim. Owner-correlated Authoritative Provider Usage from that turn is reduced into atomic Price Components and settled exactly once under ADR-0033 using the current complete pricing publication per ADR-0034; missing or conflicting components remain free. This owner records and settles work that has already happened and never authorizes provider work, replay, retry, channel fallback, or a retroactive Try.

The exception applies only to a provider-initiated OpenAI Realtime turn for which no matching client `response.create` exists. A client-originated `response.create` remains an ordinary Work Action and must complete Try before its upstream write. HTTP, Responses WebSocket, Async Task, client-created Realtime turns, and locally inferred work cannot reuse the observation path. If a deployment requires every chargeable turn to complete Try before provider work, it must disable provider-initiated VAD/idle-timeout responses or absorb their upstream cost; it cannot relabel post-work observation as Try. A non-empty unknown response ID is never inferred to belong to another active turn.

Before the first native Responses WebSocket create is written, handshake failures may try another healthy channel within the request's captured retry budget. Explicit channel pins and strict affinity remain single-owner constraints, and the final canonical provider error is delivered before closing. No channel retry is permitted after entering `WriteMessage`.

Strict Realtime affinity is a persistent owner contract. Temporary owner unavailability fails the request without deleting the binding; non-strict affinity may still clear a failed preference before fallback and later rebinding.

Session close waits only a fixed 100 ms grace for an already-running typed send result；该等待只用于冻结 transport 事实和禁止重放，不决定最终收费。

Ordinary queue admission remains bounded and fail-fast when its frame/count budget is full. Translated pipelines keep bounded queues at each stage but do not share one cross-stage credit ledger, so their instantaneous retained-byte peak can be the sum of those stage bounds; this is accepted instead of adding a multi-owner event journal or distributed credit protocol.
