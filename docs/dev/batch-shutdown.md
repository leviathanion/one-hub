# 批处理与业务优雅停机

沿用 `batch_update_enabled` 开关（默认关闭）和 `batch_update_interval`（开启后默认 5 秒），没有新增配置。禁用批处理时继续直接写日志与统计，业务排空仍然执行。

收到停止信号后，先关闭 HTTP 业务准入，同时通知 HTTP 服务、活跃 WebSocket、后台任务轮询、Telegram 指令处理及进程后台运行时开始退出。HTTP handler 的完成单独计数，包括 hijack 后仍在结算的 WebSocket handler；连接关闭不是业务完成。关闭连接注册入口后，已获准请求晚创建的连接也立即进入关闭。Responses 的首次上游打开与发送 worker 由现有 actor join；普通 Realtime 的不可脱离会话在任何关闭来源都等待 Abort 完成。Codex 可脱离会话还单独等待既有会话 janitor 与 provider reader／异常清理，覆盖连接关闭后的计费 finalizer。

停止后台轮询后不发起下一轮工作；等待在途 provider 查询、已有有界结算路径退出，不向供应商自动重放请求或取消已接受的长任务。已持久化 Task 仍沿用现有恢复机制，不能从本进程退出推断上游任务失败。发布观察器、渠道缓存同步、定时任务及已启动渠道探测也必须结束；渠道流式检查沿请求 context 取消，handler 等待检查 worker 返回，结果流只有 producer 关闭。HTTP 返回后的 Responses 观察器、渠道健康更新及 Codex 导入预热在已获准请求结束后停止准入并排空。

Telegram 使用既有 updater 停止准入，并等待 dispatcher reader 和已接受的指令处理完成，避免依赖库只等 handler 时出现 reader 晚注册窗口。

上述业务生产者全部完成后才关闭支付资源、停止批次准入、等待在途刷新并执行最后一次 flush，随后才关闭数据库。整个过程共享已有 30 秒停机预算。任何生产者未能排空都返回错误并以失败状态退出，不把批处理“成功停止”当成业务成功，也不在仍有业务使用者时主动关闭 SQL。超时退出不是可靠持久化保证。

周期刷新给统计和日志各自最多 5 秒的数据库写入预算，统计超时不会耗尽日志的预算。最终刷新服从剩余停机期限，并为日志保留至少一半剩余时间（统计仍最多 5 秒）。统计和日志串行写入，避免为公平性增加并发数据库写入。日志队列最多接受 10,000 条、每种统计最多 10,000 个待写 key；满载拒绝新增项并由调用方报告错误，已有统计 key 仍可合并增量。这是条目数限制，不是字节数限制；还可能同时存在一个已取出的有界在途批次。

重复停止返回同一完成结果；关闭后入队返回明确错误。日志批次使用一个事务，统计增量与日志批次的写入失败均汇总到停止结果，之前周期刷写失败也保留。已取出的失败批次不自动放回：提交结果不确定时重放增量可能重复统计。

日志和统计是非权威用量投影，不是余额账本。数据库不可用、队列满载、提交确认丢失、SIGKILL 或断电仍可能漏投影；本修复不增加 outbox、账务迁移或重放机制。持久 Task 与结算事实继续由既有 owner/version/事务协议管理。无需 Schema 迁移；回退代码不会撤销已落盘投影。
