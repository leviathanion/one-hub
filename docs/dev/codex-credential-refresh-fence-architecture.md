# 渠道业务数据、版本控制与凭证刷新

## 最终结构

渠道的持久化结构为 `key + other + bizdata + version`：

| 字段 | 责任 | 写入者 |
| --- | --- | --- |
| `key` | 唯一凭证事实来源，支持直接输入的 key 和 OAuth 凭证 | 管理编辑、凭证服务 |
| `other` | 可编辑、可复制、可按标签同步的连接配置 | 管理编辑、配置同步 |
| `bizdata` | 按业务命名空间组织的服务端内部状态 | 对应业务服务，经数据库 CAS |
| `version` | 配置、凭证、内部业务状态和生命周期的并发版本 | 数据库写入时原子递增 |

不新增 `provider_state`，不再保留渠道专属的 `credential_revision`、`credential_refresh_fence`、`credential_refresh_started_at` 列。`version` 也不叫 `edit_version`，因为自动凭证刷新和删除同样参与并发控制；它不是资源归属版本。

`bizdata` 使用现有 GORM JSON 类型，数据库层不依赖 JSON 路径查询或数据库特有的 JSON 更新语法。静态 key 无需凭证刷新状态。当前凭证模块只拥有如下路径：

```json
{
  "credentials": {
    "refresh": {
      "attempt_id": "每次操作唯一的 UUID",
      "started_at": 1790985600
    }
  }
}
```

刷新完成后删除 `credentials.refresh`；命名空间为空时移除命名空间，其他命名空间和未知兄弟字段原样保留。token 不在这里重复存储。每个渠道最多一个未决刷新标记，没有历史列表；时间戳仅用于区分近期操作与长期未决操作，不能充当自动解锁期限。

`other` 不适合存这些状态：它是管理配置，参与表单往返、渠道复制和标签同步。将刷新门禁放入其中，会让管理操作意外复制或清除运行状态。`bizdata` 不参与这些路径，不通过普通渠道 JSON/导出暴露，也不接受编辑请求提交。新建、复制和标签新增渠道均从空业务状态、版本 0 开始。

## 责任边界

- `common/credentials`：拥有刷新状态格式、占用、提交、安全取消、独立授权恢复的通用规则。仅通过 `Store` 接口读取快照和执行 CAS，不认识 Codex、JWT 或 OAuth 端点。
- `model.ChannelCredentialStore`：读取渠道行并执行带 `id/version` 条件且仅允许存活行的单行 CAS。一次原子写入更新 `bizdata`、可选 `key` 和 `version + 1`。不解析账号，不交换 token，凭证 SQL 禁止输出到日志。
- `providers/codex`：负责 OAuth 协议、账号证据提取、请求是否已发送的分类，以及把结果交给通用凭证服务。
- 管理编辑：通用凭证策略检查未决状态；有未决刷新时禁止修改连接身份，但允许带正确版本的元数据编辑。

未来接入其他 OAuth provider 时复用凭证服务与同一路径。新的独立业务可添加自己的命名空间；需要索引、唯一约束、历史记录或独立生命周期时，再为该业务设计关系表，不将所有业务数据无条件塞进 JSON。

## 刷新与失败语义

1. 从数据库读取当前渠道，在 provider 边界确认类型仍属于当前 provider（渠道 ID 可原地改为其他类型）。类型已变更时停止刷新和旧 token 回退。使用读取到的 `version` 和唯一 `attempt_id` 占用刷新，原子写入标记并递增版本。占用失败不发起 OAuth。
2. 占用持久化后才发送 OAuth。进程内锁让同机并发请求等待胜者并复用其已提交的凭证，避免直接返回 busy；数据库标记是唯一持久化依据；不再使用 Redis 刷新租约或内存 pending 凭证补偿。
3. 成功后重新读取最新行，确认原 attempt 仍是 owner，原子写入新 `key`、移除标记、递增版本；随后才发布到 provider 和 token 缓存。
4. 元数据编辑可推进版本。凭证服务最多重试三次数据库 CAS，每次重新确认 owner 并保留最新业务数据；不会重发 OAuth。提交回执丢失时通过权威读取识别已提交结果。
5. 只有明确未发送旧 refresh token，才允许该 attempt 安全取消。请求已经发出、响应丢失、进程退出或提交最终失败时，保留标记。重启、缓存过期和等待超时都不能令旧 refresh token 自动再次可用。
6. 未决状态通过同账号的独立 OAuth 授权恢复。授权会话固定渠道 ID、账号、version 和 attempt；数据库以原快照 CAS 发布新凭证。迟到的旧提交/取消不能覆盖新凭证。
7. 请求取消后，如果已经取得新凭证，使用有界且不继承请求取消的上下文完成数据库提交。最终持久化失败不发布新 token，由后续独立授权恢复。

用量缓存是可丢弃的展示数据，不能承担凭证恢复。OAuth 更新不推进用量缓存 generation；用量条目仍按凭证指纹隔离。业务数据标记不受缓存清理影响。

## 管理编辑版本协议

- 单渠道 GET 返回 `version`，更新必须提交原始 `expected_version`，包括列表与标签子列表的快捷状态、优先级和权重操作。
- 标签 GET 返回成员 ID 到版本的 `versions`，更新必须提交 `expected_versions`。校验成员集合与每个版本；任一冲突整批回滚。
- 版本冲突返回 HTTP 409，不在服务端把旧输入套到新快照上自动重试。前端保留未保存输入，提示重新读取核对。
- OAuth 独立保存成功后，前端读取新快照。仅当配置与打开表单时一致，且凭证仍为刚保存的值时，才推进表单提交版本；未保存输入不重置。发现其他修改则保留旧版本并提示核对。
- 状态、优先级、标签、模型和配置批量修改均推进版本；用量、余额、测速等统计用独立指定列/原子增量更新，不推进版本。
- 现有“每次保存前统一提示影响范围”的交互保留。确认弹窗不能替代后端版本和刷新状态检查。

## 单机停机升级

此次采用一次性升级，不支持新旧程序同时运行，不提供运行时旧字段读取、双写或回退路径。

1. 停止整个旧实例（包含后台刷新任务），备份完整数据库和当前程序。SQLite 应在停止进程后备份；如有 WAL，确保备份包含数据库的完整一致状态。
2. 同时替换后端和前端，启动新实例。启动迁移 `202610030001` 在渠道 AutoMigrate 前执行：增加 `version/bizdata`，按批读取包括软删除渠道在内的全部行，把旧 revision 与未决刷新标记搬入新结构。
3. 数据转换事务提交后，依次删除旧 timestamp、fence、revision 三列。MySQL DDL 可能隐式提交，因此迁移支持在上述步骤中断后重启继续；这只是迁移恢复能力，不是业务兼容分支。
4. JSON 损坏或新旧 attempt 冲突时启动迁移失败，保留旧列供核查，不猜测或清除保护状态。已有未决刷新升级后仍需独立授权恢复。
5. 确认迁移成功、旧列已删除，再恢复流量。刷新浏览器，重新打开编辑表单；未完成的 OAuth 授权重新发起。

迁移不可自动逆转。若要回滚，停止新程序，恢复完整升级前数据库备份及旧程序；不能只把二进制换回旧版。

## 验证重点

覆盖静态 key、未决刷新和软删除行迁移；中断 DDL 恢复；冲突状态保留；并发占用唯一胜者；旧表单冲突；标签原子回滚；未知命名空间保留；提交回执丢失；数据库故障不触发 OAuth；请求取消后提交；失败提交不缓存凭证；新 provider 不重复兑换；同账号恢复与迟到操作隔离；SQL 凭证脱敏。

## 设计消融校验

- 删除 forced 刷新中的第二次渠道读取：第一次权威读取后已经完成凭证变化比较；CAS 负责检测之后的竞争。重复读取既增加 I/O，也可能让请求凭证与先前保存的代理配置来自不同快照。
- 同一次读取的刷新标记只解码一次；提交的三次 CAS 与最终回执确认使用同一套所有权判断，不另设一份终态分支。
- 删除未使用的凭证服务方法别名，直接调用共享服务；不保留没有测试注入用途的间接层。
- CAS 只依赖渠道 ID、version 和存活条件；所有运行时凭证/类型变更都推进 version，因此不再把 type 和整段 key 重复放入 SQL 条件。provider 类型检查仍保留在协议边界，凭证服务保留操作所有权检查。
- 保留进程内锁：消融实验中移除它后，并发第二个请求立即报 `credential_refresh_in_progress`；保留时两个请求都取得同一新 token，OAuth 仅调用一次。
- 保留持久化标记、CAS、有限 DB 重试、独立提交上下文和未决状态：测试分别覆盖新实例不能重放歧义交换、元数据竞争不丢凭证、最后一次提交丢失回执可确认、请求取消后仍能完成提交。它们不能被锁或缓存替代。
