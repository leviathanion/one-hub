# 用户管理消融实验与精简方案

## 文档状态

当前实现。已按 17 项清单实施，实验记录保留为精简设计的依据。

本方案替代此前“统一用户管理边界”的宽泛重构建议，保留[额度自动分组方案](./user-group-quota-consistency-plan.md)中已验证必要的行为。2026-09-09 已完成 16 个实验配置，包含基线、单因素删除、最小替换及组合验证；评估阶段使用临时 Go overlay，后续已将必要改动及回归测试落地。

结论：删除无人读取的用户所属组缓存、重复解绑实现和不安全的身份匹配回退；在现有模块补齐权限、身份唯一性、验证码消费和字段校验。保留资金事务、最终重算、按字段更新及必要的数据库隔离。不建设新的用户服务或通用命令框架。

## 1. 不可消融的用户要求

- 按入账后的 `quota + used_quota` 自动升降组，充值、兑换、赠送及管理员增减均计入；不新增 `recharged_quota`。
- 允许请求在途时短暂偏差；正常完成后自动收敛，少数异常可通过零额度人工重算。不能把正常结算的维护负担转给管理员。
- 资金不能重复记账，资料修改不能覆盖余额、消费、角色或组；身份归属和管理员授权不适用分组的宽松一致性。
- 保留正常注册、邀请奖励、已绑定身份登录、显式绑定/解绑及私聊查询密钥的功能。通过删除功能获得的“简化”不算有效消融。

这里“最终一致”仍以在途操作完成、规则稳定、有匹配区间为前提；没有匹配区间保留原组。人工重算不负责恢复丢失的计费证据。修改分组规则后，用户在后续额度操作或人工重算时应用新规则。

## 2. 实验方法与结果

实验使用当前工作区为基线。每个配置单独替换源文件，保存源文件指纹、变更 patch、overlay、测试命令和日志；组合实验检查单项简化同时启用后的相互影响。未修改真实数据库，未向外部发送消息。

| 配置 | 唯一变化或对照 | 实测结果 | 方案决策 |
| --- | --- | --- | --- |
| `baseline_core` | 现有额度、登录、资料等正常链路 | 通过 | 作为行为基线 |
| `baseline_defects` | 在原实现运行已发现问题的复现 | 缓存等待、旧会话权限、身份回退和凭据复用均复现 | 确认实验能够捕获缺陷 |
| `remove_cache` | 删除组缓存读取函数、key 常量和全部失效调用 | 相关链路通过；结算不再发出 Redis DEL | 删除整套缓存，不再优化其失效协议 |
| `dedup_unbind` | controller 调用现有 model 解绑函数，删除重复字段映射 | 四类身份解绑及未知类型拒绝通过；资金、组及其他身份不变 | 保留一个实现 |
| `remove_final_group` | 最终结算仅更新 Q/U，不再重算组 | Confirm/Cancel 后仍留在低组，并发终结也不收敛 | 保留最终重算 |
| `remove_used_commit` | 从最终结算移除已消费累计 | 收费后 U 缺失；余额和消费之和错误 | 保留事务内 U 更新 |
| `restore_snapshot_login` | 在登录时恢复整份旧 User 写入 | 新余额 201 被写回 200，paid 被写回 default | 保留按操作限定字段 |
| `remove_gorm_isolation` | 删除两处 GORM Session 隔离 | 充值、兑换及历史用户入账失败，出现查询状态污染 | 不能整体删除 |
| `remove_outer_gorm_session` | 只删除锁定用户前的隔离 | 充值、兑换等路径失败 | 保留外层隔离 |
| `remove_inner_gorm_session` | 只删除共享额度更新函数内的隔离 | Confirm/Cancel 等路径失败 | 保留内层隔离 |
| `atomic_code` | 同一把现有锁内校验并删除正确凭据，移除重置成功后的独立删除 | 同码二次绑定被拒绝；并发重置仅一次成功；错误输入不消耗正确码 | 合并校验和消费，无需跨存储事务 |
| `current_auth` | 在现有中间件通过 SQL 刷新角色和状态 | 降权、禁用、删除后旧管理会话均被拒绝 | 复用当前主体读取，无需授权缓存或新框架 |
| `stable_identity` | 删除 GitHub 用户名/邮箱回退及 OIDC 用户名回退 | 错误归属复现通过；GitHub 改名后稳定 ID 仍识别原用户 | 删除危险回退，历史绑定单独迁移 |
| `binding_without_constraint` | 并发绑定前各自预查占用 | 两次成功，产生两个归属 | 预查不能承担唯一性保证 |
| `binding_with_constraint` | 在同一测试库增加非空 GitHub ID 的唯一索引 | 同一身份只产生一个归属 | 数据库保证唯一性；不新增应用锁 |
| `combined` | 组合缓存删除、解绑合并、原子消费、当前授权、稳定身份匹配 | 选定正常链路与相应缺陷复现共同通过 | 可以组合实施；不表示其余已知问题已经修复 |

其中缓存实验复用同一故障注入：基线 SQL 已提交，但同步 DEL 等待约 400 ms，超过调用方 100 ms 截止时间；删除缓存后 DEL 次数为零。该实验验证依赖被消除，不把测试套件耗时当作吞吐量基准。

缓存相关测试只替换内部观察手段：直接读取预置的旧 Redis key，仍验证新请求和既有长连接下一工作单元使用 SQL 新组。没有删除“旧缓存不能影响归属”的行为断言。

### 验证范围

- 删除缓存与合并解绑的组合已执行 `go test -count=1 ./...`，通过。
- 完整最小替换组合首次全量回归发现两项失败：价格管理测试仅在 cookie 中伪造管理员、SQL 主体仍是普通用户；另一个 WebSocket 测试在未修改源码的基线中重复 20 次失败 5 次。前者在临时夹具中补齐 SQL 管理员角色，后者作为既有不稳定测试单独记录，不放宽生产授权或删除断言。
- 修正上述价格管理夹具后，完整最小替换组合再次执行 `go test -count=1 ./...`，通过。WebSocket 测试的不稳定性仍然存在，本次通过不代表修复了它。
- 最小替换组合已执行 `-race -count=3`，覆盖并发结算、并发密码重置、验证码复用、错误码保护和旧管理会话撤权，通过。
- 唯一约束实验仅验证 SQLite 的非空 GitHub ID 索引。没有证明 MySQL/PostgreSQL 迁移可直接复用该 SQL。
- 删除 U 的实验验证最终消费必须被可靠累计，没有证明所有异步架构都不可行；在不增加消息与恢复机制的当前约束下，保留已有事务最简单。
- 权限实验验证请求准入刷新，未实现管理员操作人与目标的事务内复验；后者仍属于待修复范围。

本地实验目录为 `/tmp/onehub-user-ablation-bpzKQ4`。`matrix.json` 汇总结果，`run.py` 生成并运行配置，每个配置目录包含 `mutation.patch`、`overlay.json`、`results.jsonl` 与 `summary.json`。日志中的测试通过/失败事件包含父测试和子测试，不能据此计算独立案例总数。

## 3. 最小完整实现

### 3.1 额度：保留核心，删除缓存旁支

保留 `model/user_credit.go` 的 Q/U/组更新，以及充值、兑换、奖励、管理增减、Confirm/Cancel、Task 对该规则的调用。Try 仍只预扣，不把预扣计入最终消费。保留范围校验、行锁、事务回滚、结算一次执行权和 MySQL 重复赋值的零行处理。

删除 `CacheGetUserGroup`、`UserGroupCacheKey`、`InvalidateUserCreditCache` 及调用点，并清除只为失效缓存存在的空条件、defer 和注释。该结论仅针对用户所属组缓存；分组规则发布、token 缓存和其他缓存不在删除范围。

保留零额度重算和前后分组审计。手动指定组仍可能被后续额度操作覆盖，不增加“永久固定组”状态。旧批量消费 writer 不恢复，避免同一消费被写入两次。

### 3.2 授权：复用读取，在修改处保证权限成立

现有 HTTP 中间件及 Telegram 已绑定用户入口，以数据库中的当前用户状态作为准入依据；使用现有主体读取能力，不建设新授权服务。

管理员修改、启停、升降角色、删除和额度操作，在现有 model 层明确的事务入口中接收操作人 ID，读取并核验操作人与目标的当前状态，再提交授权范围内的修改。锁多用户时采用固定顺序，并处理操作人与目标相同的情况。事务中只复用同一份权限规则，controller 不再先检查目标后调用无保护 setter。

中间件与敏感写入的检查属于两个时间边界：前者限制请求准入，后者防止检查后权限变化。不能使用中间件快照替代事务内判断。该方案不承诺撤销已经授权并开始执行的普通工作。

Telegram 的密钥查询和分页回调仅允许私聊，均检查当前绑定主体仍启用；保留正常私聊功能，不自动转发密钥。

### 3.3 身份：稳定匹配、显式绑定、数据库唯一性

GitHub 以稳定 ID 查找本地用户，OIDC 以签发方作用域内的 subject 查找。删除按用户名或邮箱自动认领旧用户的回退，以及只服务于旧用户名自动登录的配置分支。已登录绑定必须验证当前本地主体及第三方身份；不得借登录补全覆盖另一个非空身份。

在现有身份写入入口集中处理绑定和解绑，provider 仍负责自己的身份协议。不引入通用 provider 插件系统、新身份服务或新身份表；短期验证码表独立于持久身份归属。绑定归属由数据库唯一约束保证；能够将唯一冲突映射为清楚业务错误时，可删除仅为防重复而做的占用预查。

邮箱当前承担密码恢复地址，因此签发重置凭据时必须得到唯一用户 ID，并将该 ID 与恢复地址绑定到此次凭据；消费后在修改密码的事务内复验地址仍属于该用户，再按 ID 更新密码。不能在提交时仅凭邮箱重新选择另一个账号。发现历史重复邮箱时拒绝模糊恢复，不能同时修改多个账号。邮箱关联、注册、管理修改及第三方邮箱补全需遵循同一占用规则。非关键的第三方资料补全发生占用冲突时，不应把它解释为账号归属或隐式合并授权。该边界已实施，三种数据库均补充了恢复地址转移测试。

用户当前只有一个 OIDC 签发方配置，旧 `oidc_id` 只保存 subject。继续复用此字段必须约束签发方作用域：存在绑定时，切换签发方须走明确的迁移流程，不能直接按新签发方的同名 subject 登录旧用户。当前实现通过既有 OIDCIssuer 选项行锁协调登录、绑定和配置修改；存在绑定时禁止更换或移除签发方约束，过期的在途回调也不能新建绑定。环境继承值经既有选项发布协议固定，未新增用户数据库字段。

### 3.4 验证码：只保留一次授权

为满足后续明确的“多实例、三种数据库、Redis 可关闭”要求，一次性凭据统一由 SQL 持有。新增短期表 user_verifications，替换原进程内 map；Redis 不参与签发或消费，也不维护第二套后端。

校验后以包含摘要、目标用户及有效期的条件 DELETE 取得唯一执行权；错误码不消耗正确码，旧请求不能删除新凭据。摘要使用既有 session_secret 进行 HMAC 认证，多实例共享该配置。消费后 SQL 修改失败，用户重新申领，不恢复旧码或增加补偿事务。

每个邮箱与用途最多一个有效凭据，有效期 10 分钟，签发时清理过期记录。总容量限制为 10,000 条凭据，通过同表一条固定记录的行锁协调容量检查；不新增后台清理器。具体部署、迁移及失败语义见[升级说明](../deployment/user-management-upgrade.md)。

### 3.5 资料及注册：保留字段语义，减少重复映射

保留按操作限定的 patch，区分未提交与明确清空；不恢复整对象保存。自助修改直接解码可编辑字段，管理员操作校验角色、状态和组的合法性。

解绑统一复用现有 model 函数。注册继续复用已有创建和奖励入口，OIDC 将解析出的 inviter ID 传入该入口，不增加邀请奖励工作流。修复删除响应、空用户名注册及失效组限流查询等直接边界错误。

## 4. 既有 17 项问题的覆盖

以下编号固定对应用户确认的 17 项清单；#7、#8、#9 是本次实现引入的回归，其余为原有缺陷。每项单独验收，不能以全量旧测试通过代替缺陷复现测试通过。下表保留逐项判据；业务修复及对应回归测试现已落地，评估阶段的原型记录不作为单独的完成证明。

| # | 必要修复 | 完成判据 |
| --- | --- | --- |
| 1 | 管理准入读取 SQL 当前角色和状态 | 使用真实登录取得的 Cookie，在降权、禁用、删除后分别访问管理接口，全部被拒绝；有效管理员仍正常访问。原型已覆盖撤权复现。 |
| 2 | 操作人和目标的权限检查与敏感修改同事务，受锁保护 | 并发提升目标权限、降低操作人权限时，修改必须按事务中的有效权限判定；被拒绝的操作不修改密码或其他敏感字段。覆盖管理编辑、启停、角色修改、删除及额度入口，不能只修一个 controller。 |
| 3 | GitHub 登录取消邮箱回退 | 空邮箱且无稳定 ID 关联的 GitHub 身份不能选中本地空邮箱账户，包括 root；正常已绑定账号仍能登录。错误匹配原型已验证。 |
| 4 | GitHub 登录取消旧用户名回退 | 不同稳定 ID、相同旧用户名不能进入原账户；同一稳定 ID 改名后仍识别原账户。原型已验证。 |
| 5 | OIDC 登录取消用户名补绑 | 同名、不同 subject 不修改原绑定且不能登录原账户；已绑定身份正常登录。错误绑定原型已验证；签发方迁移另按第 3.3 节验收。 |
| 6 | Telegram 密钥命令与分页回调统一限制私聊 | 群聊及超级群命令、分页均不输出密钥；当前有效绑定用户在私聊中仍可查询。使用模拟 BotClient 验证目的聊天及消息内容。 |
| 7 | 自助修改保留字段是否提交的信息 | 只改密码时显示名不变；显式改名成功；合法清空按接口约定处理；无关身份、角色、资金和组不变。 |
| 8 | 管理 patch 校验角色、状态及组 | 空组、不存在或已停用的组、role=0、status=0 及其他非法枚举被拒绝且不产生部分修改；遗漏字段保持原值，合法修改成功。 |
| 9 | 删除无人读取的所属组缓存及全部失效调用 | 充值、兑换、最终结算与重算均不再对该 key 发出 DEL；SQL 资金及下一工作单元归属正确。结算故障注入和删除组合回归已验证。 |
| 10 | 删除接口准确返回结果 | SQL 删除失败返回 success=false 且用户保留；成功返回完整 JSON 和 success=true，用户不可再被正常访问；两种删除入口均覆盖。 |
| 11 | 身份创建和绑定共同受数据库唯一约束保护 | 两用户同时认领同一稳定身份最多一个成功；重复提交同一已成立归属不制造第二归属；另一方得到明确冲突。覆盖注册、绑定、补全写入以及空值/软删除数据迁移。三种数据库的唯一性、空值处理与旧数据迁移均已验证。 |
| 12 | OIDC 注册向已有创建入口传递解析出的 inviter ID | 配置非零奖励时，邀请关系、邀请人和被邀请人的奖励及分组均正确；无邀请时不额外奖励；已建立身份再次登录不重复奖励。 |
| 13 | 验证码单次消费、邮箱唯一归属、重置按凭据绑定的用户 ID 修改 | 同码重复绑定被拒绝；不同有效码也不能使同一邮箱同时归属多个用户；历史重复邮箱不得批量重置；签发凭据后地址转移不得使另一个用户被重置。另已覆盖历史重复归属、地址转移和数据库唯一性。 |
| 14 | 原子校验并消费重置凭据 | 并发重置最多一次成功，返回密码匹配最终数据库；错误码不消耗正确码；消费后 SQL 失败要求重新申领；旧凭据不能删掉新签发凭据。已验证独立进程竞争消费，Redis 开关不改变结果。 |
| 15 | Telegram 每次使用当前有效绑定主体 | 禁用或删除后，旧绑定用户的命令和分页均不能取得密钥；有效用户仍正常查询。私聊限制本身不能替代状态检查。 |
| 16 | 查询速率前处理组及限流器不可用 | 停用、删除组后的查询返回明确业务错误，不发生 panic/空响应；有效组和已有零限额配置的语义保持不变。 |
| 17 | 注册要求有效非空用户名 | 缺失、空字符串及纯空白用户名均拒绝且不创建记录；关闭邮箱验证时同样成立；正常注册仍可登录。 |

此前已修复的四项作为保护性回归保留：充值增量只计算一次；最终结算恢复预扣期间的错误分组；登录不覆盖邀请奖励形成的新组；root 邮箱修改同步运行时联系地址。

“17 项全部修复”的完成门槛是：上述逐项判据通过，受影响入口的正常链路通过，部署所用数据库的约束迁移及并发测试通过。历史冲突完成归属处理或被明确隔离，不能静默跳过后宣称修复完成。此前 16 个实验配置及全量旧测试的结果只提供设计证据，不替代这一门槛。

## 5. 不纳入本轮的设计

- 独立用户微服务、额外 service/repository 分层、通用命令总线和 provider 注册框架：现有函数与事务入口足够承载已确认规则。
- 分组事件日志、消息队列、后台重算任务、独立充值累计字段：现有结算自动收敛与人工重算已符合需求。
- 授权缓存、分布式身份锁、验证码补偿事务：没有证据表明其收益超过当前 SQL 与原子消费方案。
- 一次性重建 User 表、迁移全部身份到新表：当前没有多签发方或一类身份多重绑定需求，不承担这部分迁移成本；短期验证码存储是后续多实例要求下的必要增量。

这些未实现的设计属于范围裁剪，不宣称已逐一运行消融实验。多实例凭据消费已由 SQL 实现；未来确有多签发方、严格崩溃恢复或持续无法人工处理的分组偏差时，再对相应边界单独升级。

## 6. 迁移、实施与验收

生产升级按[用户管理升级说明](../deployment/user-management-upgrade.md)执行。先只读盘点重复身份、重复非空邮箱、旧用户名绑定及 OIDC 签发方。存量冲突不能自动选择归属；唯一约束前需要处理空字符串/零值以及软删除账号的身份占用，不能直接在现有默认空值上添加普通唯一索引。不同数据库的具体索引和空值迁移须分别验证。

在同一修复范围内删除缓存和重复实现，完成授权、身份、验证码及资料输入边界，迁移全部真实调用点。仅用于展示的旧身份字段可保留数据，但不能保留危险的自动登录回退。

身份迁移按旧实例停写、冲突处理、约束迁移、新实例启用的顺序执行；历史仅靠用户名关联的用户通过明确验证重新绑定，提供可用的账号恢复入口。身份迁移不允许回滚到不安全自动认领逻辑。额度仍遵守原方案的旧批量 U writer 排空要求，新旧消费 writer 不混跑。

验收覆盖以上 17 项复现以及正常注册/登录/绑定、邀请奖励、资料修改、私聊密钥查询、充值/兑换/结算/零额度重算。优先验证失败回滚、重复请求、权限变化、并发唯一性和旧账号迁移。数据库检查包括实际部署的 MySQL/PostgreSQL；SQLite 与 Go race 检查不能替代它们。

当前实验只能支持上述已覆盖边界的精简结论，不能证明整个仓库不存在任何其他冗余。本方案不扩大到代理协议、渠道配置及其他无关工作区变更。

## 7. 实施验证

17 项问题的业务修复及回归测试已经落地。Go 全量测试、相关并发 race 检查、前端构建均通过。真实 SQLite、PostgreSQL 17、MySQL 8.0.32 环境验证了身份唯一性、旧空值及重复邮箱迁移、管理事务行锁、OIDC 签发方隔离、恢复地址转移及过期凭据处理。

验证码竞争测试启动两个独立进程，各自使用独立连接池，其中一个开启 Redis 标志、另一个关闭，均不提供 Redis 客户端；每种数据库都只有一个进程能消费成功。MySQL 另外覆盖了旧事务快照看不到新绑定的情况，配置修改使用锁定读，不能依据旧快照切换签发方。

生产数据库尚未执行迁移，存量归属冲突需按升级说明处理。旧评估阶段记录的不稳定 WebSocket 测试保留，没有为获得全量通过而删除断言。
