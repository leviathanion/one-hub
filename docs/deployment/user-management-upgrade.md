# 用户管理安全修复升级说明

## 文档状态

当前实现。对应[用户管理消融与修复方案](../dev/user-management-ablation-plan.md)。本次只修改应用与迁移代码，不自动操作已有生产部署。

## 部署条件

支持 SQLite、MySQL 和 PostgreSQL；单实例与多实例使用同一套用户管理逻辑。所有实例必须连接同一个权威、可写 SQL 数据库；SQLite 多进程需要访问同一个支持 SQLite 文件锁的数据库文件，不是各自持有一个副本。

多实例必须配置相同且固定的 `session_secret`，它同时用于 Cookie 签名与验证码摘要认证。未固定该值时，进程重启会使原会话及验证码失效；轮换该密钥也会使未消费凭据失效。无需增加验证码专用密钥配置。

Redis 不参与当前角色、用户身份、额度自动分组或验证码消费的权威判断。开启或关闭 Redis 不改变这些语义；其他模块原有缓存和限流行为继续遵循其配置。

## 数据变化

- 新增 `user_verifications` 短期凭据表，不新增 User 数据库字段或充值累计字段。
- 非空邮箱、OIDC subject、GitHub 稳定 ID、微信 ID、Telegram ID、飞书 ID 建立唯一索引；未绑定值统一存为 SQL NULL，接口仍返回原有的空字符串或零值。
- 邮箱去除首尾空白并统一小写；规范化后存在重复归属时，迁移停止，不自动选择账号或合并数据。
- MySQL 的 OIDC、微信和飞书标识使用 `utf8mb4_bin`，避免将大小写不同的稳定身份混为一谈。
- 删除旧 GitHub 用户名回退登录配置。原 GitHub 用户名字段保留资料数据，不再用于自动认领账号。

唯一约束包含软删除用户：删除账号不会把其身份自动释放给另一个账号。确需迁移归属时，应先确认身份控制权并明确处理旧绑定。

## 升级顺序

1. 备份数据库，盘点重复身份及规范化后重复邮箱；确认旧 OIDC 绑定对应的签发方。存在绑定但缺少持久化 `OIDCIssuer` 的数据库必须先核实并补齐原签发方，不能猜测归属。
2. 停止旧实例接收新请求，排空在途结算并刷完旧批量已消费统计。暂停 Task 处理后由新版本接续，新旧消费 writer 不能混跑。
3. 只启动一个迁移主实例。迁移先检查冲突，再转换未绑定值并创建唯一约束、短期凭据表；出现冲突时先处理归属，再重试升级。
4. 迁移成功后启动其他实例。非迁移节点会检查表与唯一索引是否就绪，缺少新结构时拒绝启动。
5. 验证管理员降权/禁用后的旧会话被拒绝、已绑定第三方登录、密码重置、充值与零额度重算。旧进程内签发的验证码不迁移，用户重新申请即可。

仅有旧 GitHub 用户名绑定的账号，需要使用原本地登录方式或经身份核验的运维恢复后显式重新绑定。OIDC 不再自动按用户名关联；已登录用户可通过 OIDC 授权显式绑定。

已有 OIDC 绑定时，应用拒绝更换签发方，也拒绝通过“继承”移除其持久化约束。确需更换时，先完成旧绑定的身份迁移；登录、绑定与配置修改通过同一 SQL 选项行协调，旧签发方的在途回调不能在配置变更后建立新绑定。

## 凭据生命周期与失败语义

每个邮箱与用途最多一个有效凭据，重新签发替换旧凭据。仅存储受 `session_secret` 保护的摘要和恢复目标用户 ID，消费通过条件 DELETE 取得唯一执行权；重置密码时再次检查恢复地址仍属于该用户。

有效期为 10 分钟。签发时清理过期记录，并在同一事务内限制最多 10,000 条凭据；另有一条用于容量检查的固定记录。没有流量时不启动后台清理任务，已过期记录仍无法消费，表容量保持有界。

SQL 不可用时签发和消费报错，不回退到本地内存或 Redis。凭据消费成功后密码写入失败，用户重新申请，不恢复旧凭据。提交结果不明时也不自动重放密码修改。

## 回滚边界

不要通过回退到旧用户名/邮箱自动认领或旧 Cookie 权限判断来恢复服务。旧版本不理解新的空值约束与 SQL 一次性凭据，回滚须停写并按备份、约束和版本逐项核对；不能直接与新版本混跑。

SQL 额度原值保留，自动分组仍使用 `quota + used_quota`。历史错组可在请求结束、资金核查完成后执行零额度重算，不需补建充值累计记录。
